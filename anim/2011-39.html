本题讲解：TCP 第二次握手报文段的字段

答案：C（SYN = 1，ACK = 1，seq = 11221，ack = 11221）。

第一步：先吃透机制——SYN 为什么占一个序号

确认号 ack 的语义是"期望对方发来的下一个字节序号"：某样东西要被确认，就必须在序号空间里占一个位置。SYN 虽不携带数据，但它本身是要被对方确认的"事件"，所以规定 SYN = 1 的报文段消耗一个序号（FIN 同理）。于是"我确认了你的 SYN"只能表达为 ack = 对方 seq + 1——这就是本题确认号的全部来源。

第二步：第二次握手一身兼两职

乙接受连接时，回送的报文段同时要干两件事：

  • 确认甲的 SYN：ACK = 1，ack = 甲的 seq + 1 = 11220 + 1 = 11221；
  • 发起乙自己的同步：SYN = 1，并自选乙的初始序号 seq——它由乙独立选取，与甲的 11220 无关，取什么值都合法。

所以第二次握手必然 SYN = 1、ACK = 1：SYN = 0、ACK = 0 的 A、D 连"同步 + 确认"的姿态都没有，先排除。

第三步：四个选项对号入座

选项SYN / ACKack判定
A0 / 011221无同步无确认 ✗
B1 / 111220漏加 SYN 占的 1，等于没确认甲的 SYN ✗
C1 / 111221两职俱全 ✓
D0 / 011220同 A ✗

至于 seq = 11221：那是乙自选的初始序号，题目问"可能是"，C 完全合法。

易错点

  • ack 忘加 1（误选 B）：忽略"SYN 占一个序号"的规定——ack = 甲 seq + 1 是确认 SYN 的唯一表达方式。
  • 以为第二次握手只回 ACK（误选 A/D 方向）：乙的同步也要借这同一个报文段完成，SYN 仍为 1。
记忆锚点：SYN、FIN 都占一个序号；第二次握手 = SYN=1 + ACK=1，ack = 对方 seq + 1，seq 乙自选。
