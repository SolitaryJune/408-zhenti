## 本题讲解：找主元素——摩尔投票算法（13 分）

### 答题框架

大题按问作答：先写设计思想（两遍扫描：先投票、后验证），再写代码（关键处注释），最后写复杂度。核心一句话：一遍扫描用"抵消"找出候选主元素，第二遍扫描验证候选是否真的超过一半。

### 第（1）问：算法的基本设计思想

**先立机制：为什么"抵消"能找出主元素。** 把扫描看成一场逐个登记的对决：维护候选 c 与计数 count，count 的含义是"候选手里还有 count 张没被抵消的票"——遇到与 c 相同的元素给候选加一票；遇到不同的元素，用一张新票抵掉候选一张旧票；count 减到 0，说明"当前候选与这段区间里的对手恰好一比一抵平"，就把当前元素立为新候选重新开账。

这个机制的正确性靠两条性质，想通它们，设计思想就是自然推导：

1. **主元素若存在，一定抵不完**：主元素出现次数大于 n/2，其余元素加起来不足 n/2——就算让所有其他元素都拿去和主元素配对抵消，也只能抵掉不足一半，主元素必有剩余。所以扫描结束时手里还有票的候选，若主元素存在就只能是它。
2. **换候选不丢主元素**：count 减到 0 时扔掉的只是"候选票与非候选票恰好一比一"的一段前缀。主元素在这段里占不到便宜：它若是这段的候选，正好被对手抵平；若不是，它只是去抵消别人的票。所以丢弃这段不改变主元素"比其余元素多"的优势，优势会一路带到扫描结束。

有了这两条，设计思想分两阶段：

1. **找候选**：遍历数组，维护候选值 c 与计数 count——相同加一、不同减一、减到 0 换当前元素为新候选。若主元素 x 真的存在（出现次数大于 n/2），它"一换一抵消"后必有剩余，最终候选一定是 x。
2. **再次遍历验证**：候选只是"若主元素存在则必是它"，主元素不存在时算法照样会剩出一个候选——例如 A=(0,5,5,3,5,1,5,7) 抵消后候选是 5，但 5 只出现 4 次，不大于 8/2。所以第二遍统计候选出现次数，大于 n/2 输出该元素，否则输出 −1。（参考代码还借性质 1 省了一步：count 减到 0 连候选都没活下来，主元素必不存在，可直接返回 −1，连第二遍都不用扫。）

### 第（2）问：C 语言实现（与参考答案一致，关键处注释）

1. `int i, c, count = 1;` // c 保存候选主元素，count 计数
2. `c = A[0];` // 先设 A[0] 为候选
3. `for (i = 1; i < n; i++)` // 第一遍：找候选
4. `if (A[i] == c) count++;` // 与候选相同则计数加一
5. `else if (count > 0) count--;` // 不同则抵消一次
6. `else { c = A[i]; count = 1; }` // 计数为零时更换候选
7. `if (count > 0)` // 候选有剩余才值得验证（性质 1：主元素存在则必有剩余）
8. `for (i = count = 0; i < n; i++)` // 第二遍：重新计数
9. `if (A[i] == c) count++;` // 统计候选实际出现次数
10. `if (count > n/2) return c; else return -1;` // 严格大于 n/2 才确认

### 第（3）问：时间复杂度与空间复杂度

- 时间复杂度：两次线性遍历数组，为 **O(n)**。为什么两遍不能并成一遍：第一遍结束时只知道"幸存候选"，不回头数一遍票，就无法区分真主元素与"无主元素时的幸存者"。
- 空间复杂度：只用 c、count、i 等常数个辅助变量，为 **O(1)**。这正是它比排序（O(n log n)）或哈希计数（O(n) 空间）更贴合"尽可能高效"的原因。

### 易错点

- **只做一遍扫描就输出候选**：候选只是"若存在则必是"，缺少第二遍验证会丢分（题干第二个例子就是反例）。
- **改用排序或哈希表统计**：虽然正确，但时间是 O(n log n) 或空间 O(n)，达不到题目"尽可能高效"的 O(n) 时间、O(1) 空间。
- **判断条件写成 count ≥ n/2**：定义是严格大于 n/2；反例中 5 出现 4 次恰好等于 8/2，应输出 −1。

> 两遍扫描：先投票选候选（抵消机制保证"存在则候选必真"），再数票做验证；时间 O(n)、空间 O(1)。
