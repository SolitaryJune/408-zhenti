## 本题讲解：域名访问全程中 DNS、ARP 与交换机自学习

### 第 0 步：先立机制——一次 Web 访问前要先补齐哪些"地址"

H1 想把一个包发出去，帧里必须同时填好**目的 IP** 和**目的 MAC**。t₀ 时 H1 手里只有域名 www.abc.com，事件顺序被"缺什么补什么"推着走：

1. **域名 → IP**：向本地域名服务器（192.168.1.126，与 H1 同网段）发 DNS 查询。但发帧还需要对方的 MAC，而 H1 的 **ARP 表为空** → 先**广播 ARP 请求**找 192.168.1.126 的 MAC（为什么必须广播：目的 MAC 未知，广播是唯一能问遍全网段的方式）；DNS 服务器**单播** ARP 应答——它从请求里已经拿到了 H1 的 MAC，可以定点回复。
2. **DNS 查询 / 应答**（UDP）：拿到 Web 服务器的 IP。
3. Web 服务器在网外，包必须先交给**默认网关** 192.168.1.1（路由器 R）——H1 的 ARP 表里仍没有网关的 MAC → **第二次 ARP 广播**，路由器单播应答。
4. 封装 **HTTP 请求**帧发出 → t₁。

为什么两次 ARP 找的不是同一个对象：DNS 服务器与 H1 同网段，可直接交付；www.abc.com 在网外，下一跳永远是网关。

### 第 1）问：另一个应用层协议与封装链

t₀ 到 t₁ 期间除 HTTP 外运行的协议是 **DNS**。DNS 基于 UDP，封装链：

`DNS 报文 → UDP 数据报 → IP 数据报 → 以太网帧`

对照记忆：HTTP 报文走 `HTTP → TCP → IP → 以太网帧`，差别只在传输层。

### 第 2）问：t₁ 时刻 S 的交换表

自学习机制：交换机从端口 X 收到帧，就把"帧的**源 MAC** → X"写入交换表。为什么学的是源 MAC：交换机学习的目的是"以后往这个 MAC 发帧时知道从哪个端口出"，而回程方向与来帧相反——入端口的源 MAC 正是回程帧的去向。t₀ 到 t₁ 间触发学习的帧：

| 触发学习的帧 | 进入端口 | 学到表项 |
|---|---|---|
| H1 的 ARP 查询广播 | 4 | CC → 4 |
| DNS 服务器的 ARP 应答 | 1 | BB → 1 |
| 路由器 R 的 ARP 应答 | 2 | AA → 2 |

（CC/BB/AA 即 `00-11-22-33-44-CC/BB/AA`；ARP 应答虽是单播，源 MAC 同样触发学习。）之后的 DNS 查询/应答与 HTTP 请求都是表项已齐的单播帧，只查表转发、不再新增。故 t₁ 时刻交换表为：**CC → 4、BB → 1、AA → 2**。

### 第 3）问：H2 收到几个帧

交换机对**广播帧泛洪**（除入端口外全部转发）、对能查到表项的单播帧**定点转发**。H2 挂在端口 3，只有泛洪才轮得到它。时间线上 H2 恰好赶上两次泛洪——H1 的两次 **ARP 查询广播帧**（找 DNS 服务器 MAC、找网关 MAC），故至少收到 **2 个帧**，目的 MAC 均为 `FF-FF-FF-FF-FF-FF`。DNS/HTTP 都是单播帧，定点转发，H2 收不到。

### 易错点

- **把封装链答成 DNS → TCP → IP**：DNS 用 UDP 不用 TCP。
- **交换表漏记 BB 或 AA**：ARP 应答是单播，但源 MAC 照样触发学习。
- **认为 H2 会收到 DNS/HTTP 帧**：单播帧定点转发，泛洪的只有 ARP 查询。
- **漏掉第二次 ARP**：找 DNS 服务器和找默认网关是两次独立解析，各广播一次。

> 一句话：域名访问 = 先 DNS（UDP）后 HTTP（TCP），中间夹两次 ARP 广播；交换表学"入端口的源 MAC"；H2 只收到 2 个目的 MAC 全 F 的 ARP 广播帧。
